powercfg /requests vs a forever loop

Published 2026-09-01 · 824 Consultants LLC · Windows Grok host playbook

This is not the Modern Standby diagnosis page, not the Allow wake timers page, and not the When sharing media policy page. Sleep-vs-forever sets timeouts. Wake timers arm an RTC if sleep still happened. Multimedia sharing is one policy that can create a holder. This page is the runtime diagnostic: powercfg /requests. If DISPLAY, SYSTEM, or AWAYMODE is not None, the plan is not the liar. A named process, driver, or service is.

The problem

The sleep pack already says a 5–20 minute idle timeout eats LEXXII-Materialize-Forever. After those timeouts are Never on AC, the hourly can still look dead because something called PoRequestPowerIrp / PowerRequest and Windows will not enter sleep or will not dim, so the operator reads “the task never ran” when the session never idled. Task Scheduler shows Ready. Last run is old. The holder is elsewhere.

Four buckets. DISPLAY keeps the panel on (browser video, a full-screen player, some GPU overlays). SYSTEM keeps the machine from sleeping (audio stream, download “execution required”, a conferencing stack, some NIC / USB drivers). AWAYMODE fakes sleep with the session still running — media sharing and some OEM “instant on” paths. EXECUTION (legacy / /n) is a process that asked to stay alive. None in DISPLAY and SYSTEM while the Grok TUI is idle is the pass for this desk. A DISPLAY holder from a video you are actually watching is expected. A SYSTEM holder from “An audio stream is currently in use” with no audio is a fail.

Do not start with powercfg -requestsoverride. That is a nuclear ignore-list. It can freeze a USB hub, a dock, or a NIC into a state the other playbooks cannot heal. Name the holder. Close it or reconfigure it. Override is last, owner-only, and never a public default.

What to run (plugged-in Grok desk)

  1. Confirm the timeout layer is already done — plugged-in sleep / hibernate are not 5–20 minutes. Lid close on AC is Do nothing. Otherwise this diagnostic is noise.
  2. Elevated Command Prompt — powercfg /requests. Then powercfg /requests /n if you need the legacy EXECUTION bucket.
  3. Classify — PROCESS (Chrome, Teams, a player), DRIVER (audio, GPU, NIC, USB), SERVICE (Windows Update, a vendor updater). DISPLAY vs SYSTEM vs AWAYMODE are different clicks.
  4. Close or reconfigure the named holder — stop the video, mute/exit the conferencing stack, disable the OEM “instant on” helper, or fix the sharing-media policy if AWAYMODE / SYSTEM points at media. Do not kill the Grok TUI because it is listed as a PROCESS; an idle TUI should not hold SYSTEM.
  5. Re-run until DISPLAY and SYSTEM print None with the session actually idle. Then soak. Do not paste auth.json next to that output.
powercfg /requests
powercfg /requests /n
powercfg /energy /duration 60

/requests is the live list. /energy is a 60-second trace if the holder is intermittent (a notification, a one-shot audio blip). Save the HTML energy report locally. Do not publish it. It can name device paths and does not belong on Pages.

How it splits from the other playbooks

  • Sleep vs forever — timeouts, Modern Standby, Interactive-only logon, result 267009.
  • Allow wake timers — RTC if sleep still happened.
  • Multimedia sharing — the policy that can create a SYSTEM / AWAYMODE holder without a visible player.
  • USB selective suspend / ASPM / EEE — hardware power while awake, not a PowerRequest.
  • This page — read who is holding DISPLAY / SYSTEM / AWAYMODE right now, then close that holder. Not a plan value.

Soak test (what "passes" means)

  1. Sleep timeouts already honest on AC. Otherwise this soak is lying.
  2. Grok TUI open and idle (not a video, not a call). powercfg /requests prints None under DISPLAY and SYSTEM.
  3. A known video in a browser produces a DISPLAY (sometimes SYSTEM) holder that clears when the tab is closed. If it does not clear, the holder is a driver, not the tab.
  4. No requestsoverride on the dock NIC, USB hub, or audio device as the “fix”.
  5. No fourth Grok TUI. Last result 267009 is still-running, not a request.
