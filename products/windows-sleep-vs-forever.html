Windows sleep vs a forever loop

Creating LEXXII-Materialize-Forever is necessary and not sufficient. Sleep, Modern Standby, Interactive-only logon, and a still-running result code will make an hourly task look like it never existed. This is not systemd. This is not a fake cluster.

Failure modes that fake a dead loop

SymptomWhat it actually is
Last run 1999-11-30Windows never-run sentinel. The task has not fired since create.
Last result 267009Still running. Overlap policy must ignore a new instance — do not stack a 4th TUI.
Last result 267011Ready / last-run recorded. Not a mysterious cluster error.
Ready, never hourlyDaily trigger with no 60-minute repeat.
Ready, plugged-in onlyDisallowStartIfOnBatteries still true.
Ready, lid closedModern Standby (S0) paused user tasks. The host “looks on.”
Missed while logged outLogon mode Interactive only.
Hourly start then silenceStop-on-battery or a 2-hour runtime cap killed the process.
Do not spawn another Grok window because last result is 267009. That code means the current run is still alive. Extra TUIs still cap at three.

Heal order (Windows, not systemd)

  1. Query LEXXII-Materialize-Forever, LEXXII-Pages-Heal, LEXXII-Ship.
  2. Confirm Enabled, hourly / PT30M / PT2H repeat, batteries allowed, start-when-available on, new-instance ignore.
  3. Power settings: 5–20 minute sleep on an operator desk will eat the loop. Connected standby that freezes Task Scheduler is a host bug, not a Grok bug.
  4. Recreate the Grok durable hourly scheduler if it vanished. Honest cap: 7 days even when durable.
powercfg /a
schtasks /Query /TN "LEXXII-Materialize-Forever" /FO LIST /V

powercfg /a tells you whether S0 connected standby is the sleep that is eating the loop. Do not paste live brokerage numbers next to that output. Do not paste auth.json.
