Multimedia timer resolution vs a forever loop

Published 2026-09-01 · 824 Consultants LLC · Windows Grok host playbook

This is not the When sharing media policy page and not the Power Options row When playing video. Sharing media can pin SYSTEM / AWAYMODE with no player. When playing video is display quality while a file is actually playing. This page is the kernel interrupt period: timeBeginPeriod / NtSetTimerResolution. A leftover 1.0 ms request starves C-states. A JS setInterval pretending to be the 5m pulse goes to sleep. Grok CLI looks hung. Task Scheduler still shows Ready.

The problem

Windows default timer interrupt is 15.625 ms (64 Hz). WinMM timeBeginPeriod(1) and ntdll NtSetTimerResolution request a finer period, usually 1.000 ms or 0.500 ms. Chrome, Edge, Discord, Spotify, OBS, games, and some Node / Electron hosts request it. The request is not a Power Options Multimedia settings click. It is a process asking the kernel to fire more often.

Two lies show up on a plugged-in Grok desk after sleep and sharing-media are already honest:

Starving. A leftover 1.0 ms request keeps the package out of deep C-states. Timer interrupts stay hot. Fans rise. Task Manager looks “busy” with no ship in flight. The Interactive Grok TUI paints late or eats input. LEXXII-Materialize-Forever still prints Ready and last result 267009 (still-running). The operator thinks grok.exe is spinning. A browser that already closed the tab is holding the period.

Sleeping. Someone implements the 5m pulse as JS setTimeout / setInterval inside the TUI. Chromium background timer throttling (1 s, then ~1 min). Coarse 15.625 ms resolution plus timer coalescing. The JS loop naps. Host-forever on this Windows profile is Task Scheduler, not a JavaScript interval. Do not call timeBeginPeriod(1) to “un-sleep” that interval. That pins C-states. It does not run the hourly.

Windows 10 2004 and later made many resolution requests process-local. That does not make this page obsolete. Hidden Chromium GPU / utility processes, WASAPI exclusive, and some NtSetTimerResolution callers still move Current on ClockRes. powercfg /energy still names an Outstanding Timer Request. Measure. Do not cargo-cult TimerTool.

What to change (plugged-in Grok desk)

  1. Confirm the timeout and share layers are already done — plugged-in sleep / hibernate are not 5–20 minutes. When sharing media on AC is Allow the computer to sleep. See sleep-vs-forever and sharing media. If the desk still intends to sleep every idle, stop here.
  2. Measure Current — Sysinternals ClockRes. Default Current near 15.625000 ms. Current 1.000000 ms or 0.500000 ms with nothing playing is a requester, not a healthy idle.
  3. Name the requester — elevated powercfg /energy /duration 60, then open energy-report.html. Read Platform Timer Resolution / Outstanding Timer Request. Requested Period 10000 (100-ns units) is 1.000 ms. The path is the liar. Typical leftovers: Chrome / Edge after a closed tab, Discord, Spotify, OBS, a game launcher, a Node helper that called WinMM and never timeEndPeriod.
  4. Close the leftover. Do not raise the period to hide it — stop the named process. Do not install TimerTool. Do not bcdedit /set disabledynamictick. Do not paste a registry “timer resolution” tweak. HPET in firmware is a different clock; it is not this click.
  5. Keep the 5m pulse on Task Scheduler — LEXXII-Materialize-Forever / Pages-Heal / Ship / Compound. An idle Grok TUI should not hold 1.0 ms. A streaming reply may hold 1.0 ms while tokens paint; that should drop when the turn ends. JS setInterval(300000) is not the host loop. See windows-task-forever.
  6. Confirm, then soak — ClockRes Current returns toward 15.625 ms with no player and no live grok turn. Do not paste live brokerage numbers next to that output. Do not paste auth.json.
clockres
powercfg /energy /duration 60
powercfg /requests

ClockRes prints Maximum / Minimum / Current timer interval. Maximum near 15.625 ms is the default ceiling. Minimum near 0.500 ms is what the HAL will grant. Current is what someone is actually holding. /energy writes energy-report.html in the working directory — that report is local, not a Pages artifact. Empty /requests with Current still at 1.000 ms is this page, not a sleep holder. If ClockRes is already ~15.625 ms idle and the TUI still starves, this is not the liar — go back to boost mode or requests.

How it splits from the other playbooks

  • When sharing media — Power Options sleep / Away Mode policy. A share pin, not interrupt period.
  • When playing video — Power Options display quality while a video is actually playing. Not timeBeginPeriod. A closed player should not keep Current at 1.0 ms; if it does, that is this page.
  • powercfg /requests — who holds DISPLAY / SYSTEM / AWAYMODE right now. Timer resolution can be 1 ms with requests still None.
  • Windows task forever — the real 5m / hourly pulse. JS timers are not a substitute.
  • Grok scheduler 7-day recreate — in-product schedulers expire in 7 days. That cap is not ClockRes.
  • This page — measure Current, name the 1 ms requester, do not WinMM-keep-alive the TUI.

Soak test (what "passes" means)

  1. Sleep timeouts already honest on AC. When sharing media is Allow. Otherwise this soak is lying.
  2. Idle session, no player, no live grok turn. ClockRes Current near 15.625 ms, not 1.000 or 0.500.
  3. powercfg /energy does not list a leftover Outstanding Timer Request from Chrome / Discord / a helper that should have exited.
  4. Starting a real stream or a grok turn may move Current to 1.0 ms; ending the turn / stopping the player returns it. A Current that survives “quit the app” is a leftover process, not the TUI.
  5. The 5m fire is still a named Windows task, not a JS interval. No fourth Grok TUI. Last result 267009 is still-running, not a timer-resolution proof.
