Secondary NVMe idle timeout vs a forever loop

Published 2026-09-01 · 824 Consultants LLC · Windows Grok host playbook

This is not the Primary NVMe Idle Timeout page, not NVMe APST, not PCIe ASPM, and not DISKIDLE. Primary is the first host timer into F1. APST is the controller table. ASPM is the PCIe link. DISKIDLE is minutes on a spinning or USB disk. This page is the remaining host timer: Power Options → Hard disk → Secondary NVMe Idle Timeout. GUID d3d55efd-c1ff-424e-9dc3-441be7833010. StorNVMe Balanced default in S0 Working is 2000 ms AC / 1000 ms DC. After Primary already walked a non-operational F-state, two seconds later the driver considers deeper F2. The NVMe stays Present. The first write after a quiet gap stalls harder than F1. Task Scheduler still shows Ready. The timeout is not APST enable.

The problem

The Primary pack already tells you to unhide GUID d639518a-e56d-4345-8af2-b9f32fb26109 and raise it on AC. APST can already be Off. ASPM can already be Off. DISKIDLE can already be Never. A ship still hitch-pauses on the first write after a couple of idle seconds. Device Manager still says Present. No re-enumerate. grok.exe looks hung. schtasks still prints Ready and last result 267009. The operator thinks Git hung. Secondary NVMe Idle Timeout is still 2000 ms. Primary walked F1. Secondary walked F2. Microsoft’s in-box StorNVMe table for Balanced S0 Working is 2000 ms AC / 1000 ms DC for this GUID. That is not a 5-minute pulse.

This is not a vanished NVMe. A device that disappears is ASPM or D3. This page is Present + a deeper stall than Primary. Do not paste nvme_core.default_ps_max_latency_us=0 on this Windows profile. Do not install systemd. Do not mint a Vercel slug because the first write paused. Do not cargo-cult this GUID to 0. Zero is not “never.” Zero means StorNVMe may consider the deeper F-state as soon as Primary has already fired.

What to change (plugged-in Grok desk)

  1. Confirm the earlier layers are already done — plugged-in sleep is not 5–20 minutes. Lid close on AC is Do nothing. ASPM Off on AC. DISKIDLE Never if the row exists. APST Off where firmware exposes it, or skip if missing. Primary NVMe Idle Timeout already raised on AC. See nvme-idle-timeout, nvme-apst, and pcie-link-state-power.
  2. Unhide the row if it is missing — Secondary NVMe Idle Timeout is ATTRIB_HIDE on many images. Missing from Hard disk before this step is expected, not a skip.
  3. Power Options → Change plan settings → Change advanced power settings → Hard disk → Secondary NVMe Idle Timeout — set Plugged in to the GUID maximum. On this forever desk, 60000 ms is the pass. On battery may stay 1000 ms if the laptop actually travels.
  4. Leave Primary NVMe Idle Timeout, both latency-tolerance GUIDs, and NVMe NOPPME as siblings — those are not this click. Do not cargo-cult Secondary to zero. Zero is not “never.”
  5. Leave APST, ASPM, write-cache, and TRIM alone on this click — the timeout is not the table. Do not switch RST to Microsoft storNVMe on a public page.
  6. Leave the current plan in place — not a switch to High performance. Do not claim a fleet GPO.
  7. Confirm, then soak — query the GUID. Do not paste live brokerage numbers. Do not paste auth.json.

SUB_DISK / GUID d3d55efd-c1ff-424e-9dc3-441be7833010 is Secondary NVMe Idle Timeout. Units are milliseconds. Microsoft min 0, max 0xea60 = 60000, increment 1. Balanced S0 Working default is 2000 ms AC / 1000 ms DC — that is not a pass for this desk. 60000 ms (60 seconds) on AC is the honest host-forever ceiling this GUID allows. A 5-minute pulse can still walk F2 if the desk sits quiet longer than 60 seconds. That is a GUID limit, not a lie. If powercfg omits the GUID after unhide, this edition did not expose the knob — stop. Primary is nvme-idle-timeout. NOPPME is nvme-noppme. APST enable is nvme-apst. Do not paste nvme_core.default_ps_max_latency_us. That is Linux. This host is Windows.

Soak test

  1. ASPM already Off. APST already Off or skip. DISKIDLE already Never if present. Primary timeout already raised. Otherwise this soak is lying about the link, the table, or F1.
  2. Idle past 2 seconds (covers leftover Balanced 2000 ms) and past 60 seconds (covers the GUID max). First write to the boot NVMe is not a stall. Device Manager still says Present. No re-enumerate.
  3. Task Scheduler still has a next-run for LEXXII-Materialize-Forever. Ready + 267009 with a stalled first write is not forever if this timeout is still 2000 ms. Grok schedulers expire in 7 days even when durable. Host-forever is that named Windows task. Not systemd.
  4. Missing GUID after unhide = skip, not a red soak. Do not invent the millisecond value in the registry.
  5. No fourth Grok TUI. Last result 267009 is still-running, not proof the timeout is already 60000. 60000 is still not Never.
