Allow system required policy vs a forever loop

Published 2026-09-01 · 824 Consultants LLC · Windows Grok host playbook

This is not the powercfg /requests page, not Allow wake timers, not Allow sleep with remote opens, and not a High performance plan essay. Timeouts can already be Never. Lid can already be Do nothing. Wake timers can already be Enable. This page is whether Windows will honor a legitimate SYSTEM required request at all: Power Options → Sleep → Allow system required policy. That is SYSTEMREQUIRED. GUID a4b195f5-8225-47d8-8012-9d41369786e2. Subgroup SUB_SLEEP. Indexes: 0 = No, 1 = Yes. This host queried it before this pack was written: Balanced is already Yes on AC and Yes on DC. Confirm. Do not rewrite Yes to Yes. Do not cargo-cult No “to force sleep.”

The problem

powercfg /requests lists who is currently holding DISPLAY, SYSTEM, or AWAYMODE. That list is empty when nobody asked. Allow system required policy is the permission bit: if it is No, an app that would have set a SYSTEM required request cannot hold sleep even when the operator wants the session alive. Forum cargo-cult “set Allow system required to No so nothing can pin sleep” turns a later honest SYSTEM holder into a no-op. The Interactive Grok CLI can still look Ready in Task Scheduler while Modern Standby proceeds. Last result 267009 is still-running, not proof this bit is Yes.

This host already reads Yes / Yes. That is the pass. Do not paste wake-timer Enable onto this GUID. Do not paste remote-files sleep onto this GUID. Do not install systemd to paper over a No. Do not mint a Vercel slug because the TUI paused after someone wrote No.
