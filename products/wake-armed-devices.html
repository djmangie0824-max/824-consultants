powercfg /devicequery wake_armed vs a forever loop

Published 2026-09-01 · 824 Consultants LLC · Windows Grok host playbook

This is not the Wake on Magic Packet page, not powercfg /lastwake, not Allow wake timers, and not lid-close Do nothing. Magic Packet is one Advanced checkbox on the dedicated NIC. lastwake is who yanked the previous sleep. Wake timers are the Windows RTC list and the plan policy. Lid-close is whether the lid is a Sleep key. This page is the inventory: powercfg /devicequery wake_armed — who is allowed to yank a docked Interactive Grok desk right now. powercfg /devicequery wake_programmable is who could be armed. Those two dumps are not lastwake and not /waketimers.

Download markdown lastwake is history Magic Packet is one NIC click

The problem

A closed-lid AC desk can already have honest sleep, lid, USB suspend, and Allow wake timers. The named task still looks Ready. Then a HID bump, leftover radio, dock audio, or OEM management engine yanks S0ix / S3. The operator reads lastwake after the fact and hunts Grok. lastwake is one wake, already spent. It does not tell you who is still armed for the next nap. /waketimers names Windows RTC owners. It does not name HID-compliant mouse. The live device list is wake_armed.

OEM images often arm more than the dedicated Ethernet. A programmable device that is not armed is honest. An armed device the operator did not intend is the surprise. Empty wake_armed (powercfg prints NONE) is a pass when this desk wants only the named task / RTC — not proof the last yank was a timer. Turning the whole USB Ethernet adapter off is the wrong fix. The dedicated NIC is the ship path. This page lists names. It does not disable that NIC. Do not install systemd. Do not mint a Vercel slug because a mouse woke the lid.

Read the two lists (plugged-in Grok desk)

  1. Confirm the other layers are the wrong object or already honest — lid-close on AC is Do nothing. Allow wake timers is already the policy pack. If you only need who yanked the last sleep, stop and use lastwake. If you only need the Magic Packet checkbox, inventory here first, then that pack.
  2. Elevated Command Prompt, while the desk is awake — run the two queries below. Save the output locally. Do not publish the dump. Device instance paths do not belong on Pages.
  3. Classify every wake_armed line — dedicated USB Ethernet or dock NIC: expected if the Power Management wake checkbox is on; leave the adapter Enabled; Magic Packet is the sibling click, not a disable. HID keyboard / mouse: a bump yanks a closed lid; disarm the HID, not the lid policy. Wi-Fi or Bluetooth leftover: radio wake is not wireless power-saving and not the dedicated NIC. OEM audio, unused hub, management engine: surprise; try exact-name disarm; some firmware will not drop — skip, not a registry hack.
  4. Read wake_programmable as the candidate set — longer than armed is normal. A name only on programmable is not armed. Do not empty programmable. The pass is armed matching intent.
  5. Disarm named surprises only — powercfg /devicedisablewake with the exact string from the dump, quoted. Re-query wake_armed. Missing name after disable is the pass for that row. Device Manager → that device → Power Management → uncheck Allow this device to wake the computer is the same grant in the GUI. Leave “Allow the computer to turn off this device to save power” to the USB-suspend pack.
  6. Never disable the dedicated NIC as the inventory fix — do not uncheck the adapter Enabled bit. Do not /devicedisablewake the Ethernet string by default. Directed-wake desks keep that NIC armed on purpose.
powercfg /devicequery wake_armed
powercfg /devicequery wake_programmable
powercfg /devicedisablewake "exact name from wake_armed"

wake_armed is the live grant. wake_programmable is who could be armed. /devicedisablewake takes the exact friendly name powercfg printed — not a guess, not a truncated OEM string. Quotes are required when the name has spaces. powercfg printing NONE on armed means the live list is empty, not that lastwake is empty. /lastwake and /waketimers stay on the other packs. If disablewake errors, this driver did not expose the grant — stop. Do not invent a wake DWORD in the registry on a public page. Do not paste live brokerage numbers next to those names. Do not paste auth.json.

How it splits from the other playbooks

  • Wake on Magic Packet — NIC Advanced Magic Packet / pattern match. This page is whether that NIC (or anything else) is even on the armed list.
  • powercfg /lastwake — the previous yank. This page is who may yank the next one.
  • Allow wake timers — Windows RTC / important-only plus WakeToRun. Not a device name.
  • Lid close Do nothing — the lid is not a Sleep key. Not a HID grant.
  • USB selective suspend — the device napped. This page is the device waking the PC.
  • Unattended sleep timeout — sleep after a wake. Not the arm list.
  • This page — live wake_armed / wake_programmable inventory on a docked AC desk.

Soak test

  1. Sleep, lid, USB suspend, and Allow wake timers already honest, or this soak is lying about a different layer.
  2. Re-run powercfg /devicequery wake_armed. The dedicated NIC is still Enabled and still has a link. Armed names match intent: NIC only if directed wake is in use; no surprise HID / OEM / leftover radio.
  3. Lid closed, named task next-run still in the future. No surprise S0 from a mouse bump or a packet the operator did not send. A bump that still wakes means that HID is still armed — re-query, do not blame lid-close.
  4. wake_programmable may still list the HID. That is capability. Fail the soak only if it returned to wake_armed.
  5. Host-forever is still Task Scheduler LEXXII-Materialize-Forever. Grok in-session schedulers expire in 7 days. Isolation-empty scheduler_list is skip recreate, not a missing-forever. Not systemd. Last result 267009 is still-running, not proof the arm list is honest.
