powercfg /lastwake vs a forever loop

Published 2026-08-31 · 824 Consultants LLC · Windows Grok host playbook

This is not the Allow wake timers policy page, not the unattended re-sleep page, and not the powercfg /requests holder page. Wake-timers-forever sets Allow wake timers = Enable on AC and checks Wake the computer to run this task. Unattended-sleep is the nap after a wake. /requests names who is pinning DISPLAY or SYSTEM while the box is already awake. This page is the remaining forensic: powercfg /lastwake names who yanked the last sleep. powercfg /waketimers names what is armed now. Those two dumps are not the same object. The policy can already be honest and the session still got yanked.

Download markdown Wake timers policy first Unattended re-sleep

The problem

The wake-timers-forever pack already did the click: plugged-in Allow wake timers is Enable, not Important only. LEXXII-Materialize-Forever already has Wake the computer to run this task. Sleep after can already be Never. That work can be done and the Interactive session still looks yanked. The operator blames Grok. Task Scheduler still prints Ready and last result 267009 (still-running). The RTC policy is not the liar. A source woke the box — or woke it and left no logged-on session — and nobody named it.

Two commands, two times. powercfg /lastwake is history: one wake, last sleep, Type plus Owner or device path. powercfg /waketimers is the present: every RTC still armed to yank the next sleep. Empty last-wake is not empty wake-timers. A USB mouse bump that woke the lid-closed desk is a Device, not the hourly. A svchost.exe timer owned by Windows Update is not LEXXII-Materialize-Forever. A Power Button / lid Fixed Feature is a human, not a 5-minute pulse. Read the name. Then go to the sibling that owns that name. Do not Disable Allow wake timers because last-wake showed a HID. That is cargo-culting the policy pack backwards.

LEXXII-Materialize-Forever is Interactive-only. A wake that lands on the lock screen, a Fast User Switch, or a logged-out console did not invent a logon. Wake timers recover a logged-on session that slept. They do not fire a fourth TUI while 267009 is still-running. This Windows profile is not a Linux FULL AUTO daemon. Do not install systemd because last-wake printed Unknown. Do not paste live NLV next to a wake dump. NLV stays off Pages.

What to run (plugged-in Grok desk)

  1. Confirm the policy layer is already done — Allow wake timers on AC is Enable, not Important only. LEXXII-Materialize-Forever has Wake the computer checked. Otherwise this forensic is noise. See wake-timers-forever.
  2. Elevated Command Prompt, after the yank — powercfg /lastwake. Then powercfg /waketimers. Then powercfg /devicequery wake_armed if last-wake named a Device and you need the live arm list.
  3. Classify last-wake Type — Timer (scheduled task or svchost owner), Device (USB HID, NIC, PCI, hub), Fixed Feature (Power Button, Sleep Button, lid, RTC clock), or empty / Unknown. Friendly Name and Instance Path are the name. Do not stop at “something woke.”
  4. Classify wake-timers owners — this list is what will yank the next sleep. LEXXII-Materialize-Forever may appear when a next-run is due while sleep is allowed. Windows Update, Automatic Maintenance, OEM updaters, and a third-party RTC are extra. Empty with Enable + a next-run still in the future can be honest. Empty after a missed hour with next-run in the past is a fail on the policy pack, not this one.
  5. Act on the named source, not the plan — Timer that is not LEXXII: uncheck Wake the computer on that task. Device that is a mouse/keyboard bump: expected; do not unplug the HID to “heal” Grok. Device that is a NIC: WoL / Magic Packet, not Allow wake timers. Fixed Feature Power Button: human. Then soak. Do not paste auth.json next to that output.
powercfg /lastwake
powercfg /waketimers
powercfg /devicequery wake_armed
powercfg /devicequery wake_programmable
schtasks /Query /TN "LEXXII-Materialize-Forever" /FO LIST /V

/lastwake is the last sleep’s source. It persists until the next sleep, so a USB bump from this morning still prints after you already healed the hourly — re-sleep once if you need a fresh sample. /waketimers is live. wake_armed is which devices are allowed to wake right now. wake_programmable is which devices can be armed. Event Viewer → Windows Logs → System → Power-Troubleshooter Event ID 1 is local corroboration of the same last wake. Save it locally. Do not publish the event XML. Device paths and volume names do not belong on Pages.

How it splits from the other playbooks

  • Allow wake timers — the policy click. Enable on AC plus WakeToRun. This page assumes that work is already done.
  • System unattended sleep timeout — the nap after a wake. This page names who woke.
  • powercfg /requests — holders while awake. This page is the source of the last sleep/wake, not DISPLAY/SYSTEM.
  • Windows Task Scheduler forever — creating the named tasks.
  • Sleep vs forever — timeouts, Modern Standby, Interactive-only logon, result 267009.
  • This page — read /lastwake and /waketimers after the RTC policy is honest, then blame the named source.

Soak test (what "passes" means)

  1. Allow wake timers on AC is already Enable. WakeToRun on the named task is already checked. Otherwise this soak is lying.
  2. A known lid-open or power-button wake prints Fixed Feature or Device HID — not a fail. Classify it. Do not “fix” it by Disabling the plan.
  3. A forced short sleep that ends at the next hourly prints Timer with the named LEXXII task as owner. Last Run Time moved. No human opening the lid.
  4. powercfg /waketimers during a window where sleep is allowed and a next-run is due can list the named task. Extra OEM / Update timers are named, then those tasks lose WakeToRun. They are not ignored.
  5. A USB mouse bump is classified as Device. The hourly is not blamed. No fourth Grok TUI. Last result 267009 is still-running, not a last-wake.
