NVMe install order that doesn’t brick Ubuntu on a local AI host

Published 2026-08-04 · 824 Consultants LLC · Problem-first notes (criteria before product links)

Local AI hosts die more often from bad storage procedure than from bad model choice. This page is the evaluation gate we use before any NVMe earns a recommendation on this site.

The job, not the SKU

We care about three outcomes only:

  1. Ubuntu boots cleanly after the drive is installed (no silent firmware / boot-order traps).
  2. The drive survives sustained write load from model weights, vector stores, and logs without lying about endurance.
  3. What arrives matches the product page (capacity, DRAM/cache class, warranty).

Install order we actually use

  1. Image the OS on a known-good medium first when the host is new. Do not dual-purpose a half-configured NVMe as the only boot device until you have a recovery path.
  2. Confirm UEFI boot order and that the board sees the drive as NVMe, not as a mystery SATA alias.
  3. Partition with a modern GPT layout (EFI + root, optional separate data). Avoid exotic RAID for single-host operator boxes unless you already own the failure mode.
  4. Run a short write soak (fio or similar) before moving irreplaceable model caches onto the drive.
  5. Record SMART / health baseline the day it goes into production so future drops are measurable.
If a vendor page hides whether the drive is DRAM-less, or buries TBW under marketing, it fails our “would we buy this with zero commission?” gate until we can verify endurance in real use.
